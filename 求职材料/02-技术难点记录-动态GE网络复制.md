# 技术难点记录：动态 GameplayEffect 的联机复制问题

> 项目：UE5 Aura（GameplayAbilitySystem 学习项目）
> 时间：2026-10-12 ~ 2026-10-13
> 关键词：GAS / 网络复制 / ReplicationMode / 动态 GE / 客户端预测

---

## 一、现象

在 **Listen Server + 2 客户端** 的联机环境下测试时，出现以下问题：

1. **玩家被电击（Electrocute）触发 Stun 后**：**服务器端一切正常**（Tag 挂上、动画播放、无法移动），**客户端毫无反应**（人还能跑能放技能）。
2. **控制台持续报错**（每次施加 Debuff 必现三次）：

```
LogNetPackageMap: Warning: FNetGUIDCache::SupportsObject:
    GameplayEffect /Engine/Transient.DynamicDebuff_My_DamageType.Lighting NOT Supported.

LogAbilitySystem: Error: FActiveGameplayEffect::PostReplicatedAdd
    Received ReplicatedGameplayEffect with no UGameplayEffect def. (BP_My_AuraPlayerState_C_1)

LogAbilitySystem: Error: Received PreReplicatedRemove with no UGameplayEffect def.
```

3. **矛盾现象**：同样是动态 GE 挂的 Debuff，**敌人被火球打中时，客户端的燃烧特效完全正常**。

> 「为什么敌人正常、玩家不正常？」是本问题最关键的突破口。

---

## 二、排查过程

### 第一步：识别报错含义

从 `NOT Supported` 和 `no UGameplayEffect def` 判断：**服务器造出来的 GameplayEffect 对象，客户端解析不了**。

查看代码，定位到 `Debuff()` 的造 GE 方式：

```cpp
// Source/Aura/Private/MY_AbilitySystem/My_AuraAttributeSet.cpp
const FString DebuffName = FString::Printf(TEXT("DynamicDebuff_%s"), *DamageType.ToString());
UGameplayEffect* Effect = NewObject<UGameplayEffect>(GetTransientPackage(), FName(DebuffName));
```

**GE 被造在 `GetTransientPackage()` 里** —— 这是 UE 网络复制的硬限制区：TransientPackage 中的对象没有稳定路径，`NetGUIDCache` 无法解析。

**结论：动态 GE 对象本身无法参与网络复制。** 这是 UE 的硬性限制，改任何参数都绕不开。

### 第二步：第一次误判（被实测推翻）

基于第一步，我给出的结论是：

> **动态 GE = 只在服务器有效，它挂的 Tag 也一定挂不到客户端。**

但用户实测反馈：**客户端能看到敌人身上的燃烧特效** —— 而特效正是靠动态 GE 挂的 `Debuff.Burn` Tag 驱动的。

**结论被推翻。** 说明「GE 对象不能复制」和「Tag 不能复制」是两件不同的事。

### 第三步：插桩验证 —— 确认客户端从未执行

在 `Debuff()` 入口和出口各插一条打印，标记当前端（服务器/客户端）和 Tag 挂载情况：

```cpp
UE_LOG(LogTemp, Warning, TEXT("[Debuff诊断-前] 端=%s 类型=%s 目标=%s 已有Burn=%d 已有Stun=%d"), ...);
// ... Apply ...
UE_LOG(LogTemp, Warning, TEXT("[Debuff诊断-后] 端=%s 类型=%s 应用后Burn=%d 应用后Stun=%d"), ...);
```

**日志结果（决定性证据）：**

```
[Debuff诊断-前] 端=服务器 类型=My_DamageType.Fire     目标=BP_Goblin_C_2 已有Burn=0 已有Stun=0
[Debuff诊断-后] 端=服务器 类型=My_DamageType.Fire     ... 应用后Burn=1 应用后Stun=0
[Debuff诊断-后] 端=服务器 类型=My_DamageType.Lighting 目标=BP_Goblin_C_4 应用后Burn=0 应用后Stun=1
```

**全程只有「端=服务器」，一次「客户端」都没有。**

→ **客户端从未执行过 `Debuff()`**，它身上的 Burn Tag **必定是服务器复制过来的**。
→ 证明「动态 GE 的 Tag 无法复制」这个结论是错的。

### 第四步：查源码，找到真正的分界线

既然 Tag 能复制，那为什么玩家不行？逐行排查 ASC 的复制配置，发现关键差异：

```cpp
// 玩家 —— Source/Aura/Private/My_Controler/My_AuraPlayerState.cpp:15
AbilitySystemComponent->SetReplicationMode(EGameplayEffectReplicationMode::Mixed);

// 敌人 —— Source/Aura/Private/My_Character/Enemy_Characte.cpp:75-76
AbilitySystemComponent->SetIsReplicated(true);
AbilitySystemComponent->SetReplicationMode(EGameplayEffectReplicationMode::Minimal);
```

**玩家是 `Mixed`，敌人是 `Minimal`** —— 这就是分界线。

---

## 三、根因

`EGameplayEffectReplicationMode` 决定了 ASC **复制什么内容**，进而决定了动态 GE 的 Tag 能否到达客户端：

| 模式 | 适用对象 | 复制内容 | 动态 GE 的 Granted Tag 能到客户端？ |
|---|---|---|---|
| `Full` | 单人 / 专用服务器 | GE + Tag + Attribute 全量 | ✅ 能 |
| **`Mixed`** | **玩家** | GE **只发给 Owner 客户端**（因为要做预测） | ❌ **不能**（要复制 GE 本体 → 动态 GE 无定义 → 连 Tag 一起丢失） |
| **`Minimal`** | **敌人 / AI** | **只复制 GameplayTag + GameplayCue**，不复制 GE 本体 | ✅ **能**（压根不需要 GE 的定义） |

**机理说明：**

- **`Minimal` 的设计初衷**是「AI 这类不需要在客户端跑完整 GAS 逻辑的单位」。它只把 **Tag 变化和 GameplayCue 广播**出去，**根本不打算把 GE 对象发给客户端**。所以哪怕 GE 是 TransientPackage 里的动态对象，**Tag 照样随 ASC 的 `GameplayTagCountContainer` 复制过去** ✅
- **`Mixed` 是给玩家做客户端预测（client-side prediction）用的**，它**真的会去复制 GE 本体**（因为要支持预测回滚）。动态 GE 没有稳定路径 → `SupportsObject` 返回 `NOT Supported` → **GE 和它携带的 Tag 一起丢失** ❌

**这就完美解释了「矛盾现象」：**

| 现象 | 目标 | ASC 模式 | 结果 |
|---|---|---|---|
| 火球打敌人，**客户端能看到燃烧特效** | 敌人 | `Minimal` | Tag 复制成功 ✅ |
| 电击打玩家，**客户端 Stun 不触发** | 玩家 | `Mixed` | Tag 复制失败 ❌ |

**三条报错对应的 GE 生命周期：**

| 报错 | 发生时机 |
|---|---|
| `SupportsObject ... NOT Supported` | 服务器**打包**时，发现 TransientPackage 对象没有稳定路径 |
| `PostReplicatedAdd ... no def` | 客户端**想挂上**这颗 GE 时，找不到 GE 定义 |
| `PreReplicatedRemove ... no def` | GE 持续 5 秒后过期，客户端**想摘掉**时再次失败 |

> **补充关键认知**：客户端看到的「掉血」并**不是**客户端自己算出来的伤害，
> 而是 **`Health` 属性本身在复制**（属性走独立通道，`ReplicatedUsing = OnRep_Health`）。
> 这两件事必须分开理解 —— 否则会误以为「动态 GE 的 Modifier 生效了」。

---

## 四、方案

### 主方案：复制 bool + OnRep（教程模式，已实施）

**核心思路**：**不再依赖 Tag 来判断状态**，改用「服务器决定 → Actor 属性复制 → 客户端本地响应」的模型。

```cpp
// MyCharacter_Base.h
UPROPERTY(ReplicatedUsing = OnRep_Stunned, BlueprintReadOnly, Category = "My_Combat")
bool bIsStunned = false;

UFUNCTION() virtual void OnRep_Stunned();
```

```cpp
// MyCharacter_Base.cpp —— 服务器侧：靠 Tag 判断，写入 bool
void AMyCharacter_Base::StunTagChanged(const FGameplayTag CallBackTag, int32 NewCount)
{
    bIsStunned = NewCount > 0;
    GetCharacterMovement()->MaxWalkSpeed = bIsStunned ? 0.f : BaseWalkSpeed;
}

void AMyCharacter_Base::GetLifetimeReplicatedProps(TArray<FLifetimeProperty>& OutLifetimeProps) const
{
    Super::GetLifetimeReplicatedProps(OutLifetimeProps);
    DOREPLIFETIME(AMyCharacter_Base, bIsStunned);
}
```

```cpp
// Aura_Character.cpp —— 客户端侧：收到 bool 后，本地挂"输入屏蔽"Loose Tag
void AAura_Character::OnRep_Stunned()
{
    FGameplayTagContainer BlockedTags;
    BlockedTags.AddTag(GameplayTags.My_Player_Block_CursorTrace);
    BlockedTags.AddTag(GameplayTags.My_Player_Block_InputHeld);
    BlockedTags.AddTag(GameplayTags.My_Player_Block_InputPressed);
    BlockedTags.AddTag(GameplayTags.My_Player_Block_InputReleased);

    if (bIsStunned) { AuraASC->AddLooseGameplayTags(BlockedTags); }
    else            { AuraASC->RemoveLooseGameplayTags(BlockedTags); }
}
```

**为什么这个方案能行 —— 三个关键点：**

1. **`bIsStunned` 是 Actor `UPROPERTY`，走 Actor 属性复制通道**，**完全不受 ASC 的 `ReplicationMode` 影响** → 必定能同步到客户端
2. **客户端不依赖 Tag** → 彻底绕开动态 GE 不复制的问题
3. **`AddLooseGameplayTag` 是本地开关** → 挂在本地 ASC 上，客户端自己挂自己用，**根本不需要复制**

### 辅助方案：动画打断两端都做

电击松手后，敌人会「先播受击动画、再切眩晕动画」。原因是 `Activation Blocked Tags` **只在激活那一刻检查**，**无法打断已经在播的蒙太奇**。

```cpp
// 服务器：StunTagChanged 里
if (bIsStunned) { StopStunMontages(); }

// 客户端：OnRep_Stunned 里
if (bIsStunned) { StopStunMontages(); }

void AEnemy_Characte::StopStunMontages()
{
    if (USkeletalMeshComponent* MeshComp = GetMesh())
        if (UAnimInstance* AnimInst = MeshComp->GetAnimInstance())
            AnimInst->Montage_Stop(0.1f);
}
```

**为什么两端都要停**：**动画蒙太奇的表现只归客户端管**，服务器调 `Montage_Stop` **不会同步**给客户端。服务器侧停是为了逻辑干净，客户端侧停才是真正能看到的效果。

### 治本方案（暂缓，学习完成后实施）

把 `Debuff()` 里的**动态 GE 换成资产 GE**（在 Content 里创建 `GE_Debuff_Burn` / `GE_Debuff_Stun` 蓝图资产，代码用 `TSubclassOf<UGameplayEffect>` 引用）：

| 方案 | 改资产 | 客户端拿到 Tag | AnimBP 要改 | 适用 |
|---|---|---|---|---|
| ① **GE 资产 + `TSubclassOf`** | 是 | ✅ | 不用 | 一切（含 DOT）**工业标准** |
| ② `AddReplicatedLooseGameplayTag` + Timer | 否 | ✅ | 不用 | 纯状态型（Stun） |
| ③ **复制 bool + OnRep**（本次采用） | 否 | ❌ | 要改 | 单状态查询 |
| ④ GameplayCue | 是 | — | — | 纯特效 |

## 五、取舍

### 为什么最终选了方案 ③（复制 bool + OnRep）

| 维度 | 评估 |
|---|---|
| **改动范围** | 小 —— 只加一个 bool 属性和两个函数，不碰资产结构 |
| **风险** | 低 —— 不影响现有技能/AI 逻辑 |
| **代价** | AnimBP 需改为读 `bIsStunned` 变量（不再读 Tag）；Bad Data 是「状态查询」型的，够用 |
| **不解决的问题** | GE 的 Modifier（数值）仍不复制 —— 但本项目「掉血」靠 `Health` 属性复制，**实际体验不受影响** |

### 为什么没选方案 ①（资产 GE）

- **它是工业标准，是治本方案**，但需要重构 `Debuff()` 的整体结构 + 在编辑器里新建资产
- **当前学习阶段优先级是「跟完教程、建立完整认知」**，不是「把项目做得最标准」
- **决定：暂缓**。标记为「教程完成后的第一个自主技术改进点」

### 为什么没有把玩家 ASC 改成 `Minimal`（消音报错）

改一行就能让报错消失，但**会破坏玩家的客户端预测能力** —— 技能按下后要等服务器回包才能响应，操作手感变差。**不划算，未采纳。**

### 关于报错：「已知且接受」

学习阶段**保留现状、不处理**。原因：
- 报错**不影响任何实际功能**（`bIsStunned` 照样同步、Stun 照样生效）
- 它是「复制失败的残骸」，不是「功能失败」
- 换资产 GE 属于重构，**留到教程完成后**

## 六、这个案例能证明什么能力（面试话术）

> 「我在做 UE 的 GAS 联机项目时遇到一个问题：玩家被眩晕后，服务器正常但客户端没有任何反应，控制台还持续报 `Received ReplicatedGameplayEffect with no UGameplayEffect def`。
>
> 我最初的判断是『动态 GE 无法复制，所以它挂的 Tag 也一定到不了客户端』。但测试时发现一个反例 —— **敌人身上的燃烧特效在客户端完全正常**，而那个特效正是动态 GE 挂的 Tag 驱动的。这说明我的结论有问题。
>
> 于是我在施加 Debuff 的入口和出口插了日志来确认执行端，结果**全程只有服务器在跑**，一次客户端都没有。这就证明了客户端身上的 Tag 只能是复制来的。
>
> 顺着这条线去查 ASC 的复制配置，最终定位到根因是 **`EGameplayEffectReplicationMode` 的差异**：玩家的 ASC 是 `Mixed` 模式，它**真的会去复制 GE 本体**（因为要支持客户端预测），而动态 GE 是 TransientPackage 对象、没有稳定路径，所以复制失败，连 Tag 一起丢了；敌人的 ASC 是 `Minimal` 模式，它**只复制 Tag 和 GameplayCue、根本不发 GE 对象**，所以动态 GE 的 Tag 照样能到客户端。
>
> 修复上我选择了**复制 bool + OnRep** 的方案：因为 `bIsStunned` 是 Actor 属性，走的是属性复制通道，**完全不受 ASC 模式影响**，客户端收到后自己在本地挂 Loose Tag。这样既绕开了动态 GE 的限制，又不用重构整个技能系统。
>
> 另外我还发现 `Activation Blocked Tags` 只能阻止技能激活、**无法打断已经在播的蒙太奇**，所以动画打断需要在服务器和客户端两端都做。
>
> 至于那个报错，它其实不影响功能，我在学习阶段先接受了它，把『换成资产 GE』作为后续的重构项。」

**这段话证明的四项能力：**
1. **能读懂网络复制模型**（`ReplicationMode` 三种模式的差异，不是背概念，是有实测支撑）
2. **能用日志反推根因**（插桩定位执行端）
3. **能推翻自己的错误假设**（发现反例后主动修正，而不是硬撑）
4. **有工程取舍意识**（知道什么该改、什么可以接受、为什么）
